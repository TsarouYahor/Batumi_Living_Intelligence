# Batumi Living — конфигурация управления агентами

Это стартовый набор **политик и инструкций**, а не действующий сервис оркестрации. Русский — основной язык коммуникации агентов; технические ключи JSON/YAML, пути и имена Git-веток остаются английскими.

## Состав
- `AGENTS.md` — правила для всех агентов и языковая политика.
- `agents/orchestrator.md` — обязанности и алгоритм оркестратора.
- `orchestrator/policy.yaml` — разрешения и лимиты (источник истины).
- `orchestrator/schemas/task.schema.json` — схема задач.
- `.github/PULL_REQUEST_TEMPLATE.md` — формат отчёта агента в Pull Request.

## Одобрение задач и предел оценок
- Оркестратор вправе создавать **предложения** задач с оценкой не более 4 часов.
- Любая задача перед исполнением требует явного согласования владельца продукта на конкретную редакцию задачи (ID + версия/хеш).
- До согласования статус `awaiting_task_approval`; только после согласования и закрытия зависимостей задача переходит в `ready`.
- Одобрение задачи не означает согласия на merge/deploy/архитектуру/платные API.
- Для надёжного исполнения требуется отдельная серверная проверка авторизации; комментарий сам по себе недостаточен без проверки автора.

## Подключение
1. Скопировать файлы в репозиторий проекта.
2. Защитить `main`: разрешить изменения только через PR, обязательные CI и независимое ревью; запретить force push. При необходимости добавить CODEOWNERS.
3. Выдать агентам токены **без** разрешений на merge, изменение защиты веток, управление секретами и production-деплой.
4. В исполнительном сервисе реализовать проверку `orchestrator/policy.yaml` **перед каждым действием с побочными эффектами**. Для ограниченных действий — отдельно аутентифицированное согласование человека.
5. Привязывать согласование к точному объекту (например, PR и commit SHA); при изменении объекта запросить согласование заново.
6. Настроить отдельные worktree/контейнеры, минимальные права, сетевые ограничения и отсутствие доступа к production-данным.
7. Настроить CI: typecheck, lint, unit/integration-тесты, проверку зависимостей и поиск секретов; при недоступности обязательных проверок — блокировать слияние.
8. Проверить учебную задачу в непроизводственной среде: даже при прямой просьбе агент не должен иметь технической возможности сливать код или выполнять deploy без внешнего разрешения.

## Важно
Markdown и YAML **не являются защитным механизмом сами по себе**. Реальное соблюдение правил обеспечивается GitHub Rulesets, ограничениями credential scopes и авторизацией на стороне сервера. После перевода системные значения и структура схем остались совместимыми с исходным набором.


## Стандарт идентификаторов задач v1.3
- Формат ID: `<PREFIX>-<NUMBER>`; номер начинается с `001`, минимум три цифры, например `FE-001`.
- Префиксы: `OR` — Orchestrator, `AR` — Architect, `DA` — Data Research, `BE` — Backend, `FE` — Frontend, `AI` — AI Analyst, `QA` — QA/Security.
- Каждая роль ведёт собственную последовательность. ID назначается при создании задачи, глобально уникален и впоследствии не меняется. Удалённые номера повторно не используются.
- ID всегда соответствует `owner_role`; зависимости могут ссылаться на задачи любых ролей.
- При передаче задачи другой роли создаётся новая задача с новым ID и ссылкой на исходную, а старая закрывается или помечается как заменённая.
- Оркестратор выделяет номера атомарно через единый реестр или через уникальные GitHub Issues под контролем сервиса: нельзя вычислять следующий ID только по локальному списку задач.
- Существующие исторические задачи вида `BL-001` не переименовываются автоматически: их можно сохранить как legacy-ссылки, но новые задачи создаются только с рольными префиксами.
- Согласование запуска привязано к ID **и редакции** задачи; изменение её существенных условий требует нового согласования.

## Дополнение v1.4: GitHub Issue approvals

См. `orchestrator/approval/README.md`. Workflow `.github/workflows/task-approval.yml` регистрирует решение владельца через комментарий и labels. **Автозапуска агентов нет**. Проверка: `node --test tests/*.test.cjs`. Новые ID задач: OR, AR, DA, BE, FE, AI, QA. Прежняя политика v1.3 остаётся в силе.
