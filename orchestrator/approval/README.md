# Согласование задач через GitHub Issues

## Использование

1. Установите repository variable `PRODUCT_OWNER_LOGIN` — точный GitHub login владельца продукта.
2. Создайте labels: `task:proposal`, `approval:approved`, `approval:rejected`.
3. Запретите неавторизованным пользователям запись в репозиторий; ветку `main` защитите Ruleset с обязательными CI, review и запретом прямого push.
4. Оркестратор создаёт Issue по шаблону с ID роли, описанием, временем <= 4 часов, зависимостями и критериями приёмки.
5. Запишите SHA-256 (первые 16 hex) *текущего Markdown-тела Issue* без CRLF. Команда: `gh issue view NUMBER --json body --jq .body | ...` может добавить перевод строки, поэтому лучше используйте утилиту API ниже или программно рассчитайте revision из API body.
6. Product Owner оставляет **собственный комментарий** `/approve-task FE-001 <revision>` либо `/reject-task FE-001 <revision>`.
7. Workflow проверяет GitHub login, ID, revision и уникальность ID, ставит label и публикует запись решения.

## Существенные ограничения прототипа

- Workflow **НЕ запускает** агентов. Состояние `approval:approved` — только сигнал, не разрешение делать произвольные действия. Будущий runner обязан сверять issue body/revision, текущий статус, зависимости и конкретные права **непосредственно перед запуском**.
- Защиту GitHub обеспечивают Rulesets/branch protection, не Markdown-файл.
- GitHub Issue можно отредактировать после approval. Поэтому label без проверки текущей ревизии **нельзя** считать действительным доказательством согласования. Для production нужна отдельная защищённая запись approval (например GitHub Environment protected reviewers или БД с signed audit log). В этом прототипе после редактирования статус визуально может оставаться approved, но runner должен считать его недействительным.
- Нумерация по ролям должна выдаваться атомарным регистратором. Шаблон использует пример FE-001; до реализации регистратора ID назначайте вручную и проверяйте уникальность. Прототип не гарантирует непрерывность нумерации при удалении Issue.
- Только команда автора с точным `PRODUCT_OWNER_LOGIN` принимается; название login нужно конфигурировать, а не подставлять произвольного пользователя.
- Лимит 4 часа и заполненность критериев пока проверяются при ручном ревью, не workflow; полноценная машинная проверка — следующий шаг.
- Отдельное согласование merge в `main` и production deployment обязательно.
